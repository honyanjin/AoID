# AoID (Association of Independent Developers) 프로젝트 현황 보고서

**작성일자**: 2026년 7월 29일 (1차)
**작성대상**: AoID 프로젝트 전체 (Frontend, Backend, Database, Nginx, CI/CD, 문서 및 스크립트) — **NewsMaker 제외**
**분석방식**: 저장소 내 소스 코드 및 설정 파일 실독(實讀) 기반. 런타임 실행 검증은 수행하지 않았으며, 실행으로 확인하지 않은 항목은 본문에 명시함.

## 4. 백엔드 아키텍처 상세

### 4.1 진입점 `backend/src/index.ts` (173줄)

부팅 순서는 `dotenv.config()` → `process.env.TZ = 'Asia/Seoul'` → `./config/env` → `./config/passport` → `./config/database`입니다. 환경변수 로드를 라우트 import보다 앞에 배치해 `env.ts` 검증이 먼저 실행되도록 했습니다.

미들웨어 등록 순서:

| 순서 | 미들웨어 | 설정 |
| :--- | :--- | :--- |
| 1 | `cors()` | `origin: env.FRONTEND_URL` (단일 문자열), `credentials: true` |
| 2 | `cookieParser()` | JWT httpOnly 쿠키 파싱 |
| 3 | `express.json()` | `limit: '50mb'` |
| 4 | `express.urlencoded()` | `limit: '50mb'`, `extended: true` |
| 5 | `requestCaseConverter` | body의 snake_case → camelCase |
| 6 | `passport.initialize()` | 세션 미사용 |
| 7 | `express.static('uploads')` | `/uploads` prefix |

등록된 라우트 prefix (등록 순서, 총 33개 + 인라인 `/health`):

```
GET /health (인라인)
/api/auth, /api/posts, /api/comments, /api/admin, /api/admin/grades,

/api/multiple-choice-tests, /api/dev-spectrum/intro,
/api (sitemapRoutes -> /api/sitemap.xml), (prefix 없음) seoRoutes
```

`/api/admin`이 `/api/admin/grades`보다 먼저 등록되지만 `adminRoutes`에는 `/grades/active`만 있어 fall-through로 `gradeRoutes`에 도달합니다. `pageContentRoutes`와 `sitemapRoutes`가 모두 `/api`에 마운트됩니다. `seoRoutes`는 prefix 없이 `/seo/...`와 `/api/seo/og-image`를 직접 서빙합니다.

`startServer()`에서 `pool.query('SELECT NOW()')`로 DB 연결을 검증한 뒤 `initSubscriptionScheduler()`, `initAiActivityScheduler()`를 호출합니다. `SIGTERM`/`SIGINT` 시 스케줄러 stop → `server.close()` → `pool.end()` → `exit(0)`, 30초 후 강제 `exit(1)`의 Graceful Shutdown이 구성되어 있습니다.

404 핸들러 → 에러 핸들러 순으로 최종 등록되며, 에러 핸들러는 `development`에서만 `err.message`를 노출합니다.

### 4.3 `middleware/`

**`auth.ts` (94줄)** — `extractToken(req)` 우선순위는 ① `req.cookies['auth_token']` ② `Authorization: Bearer` 헤더 ③ null입니다.

| 함수 | 동작 |
| :--- | :--- |
| `authenticate` | 토큰 없음 → 401. `jwt.verify(token, process.env.JWT_SECRET!)` → `req.user = decoded`(`{userId, email, role}`). 실패 → 401. **동기, DB 조회 없음** |
| `isAdmin` | `req.user.role !== 'admin'`이면 403 |
| `optionalAuthenticate` | 토큰 없음/검증 실패 모두 catch 후 `next()` — 절대 에러를 내지 않음 |
| `requireEmailVerified` | async, `users.email_verified` DB 확인 후 403 `{code:'EMAIL_NOT_VERIFIED'}`. **현재 어떤 라우트에도 미적용** |

`process.env.JWT_SECRET!`을 직접 읽어 `config/env`의 기본값을 경유하지 않습니다.

**`postValidation.ts` (285줄)** — 게시글 검증의 중심입니다.

- 제목 200자, 본문 50MB / 3,000줄(plain text 기준), 태그 10개·30자·공백불가·중복불가, 대표이미지 URL 4,096자
- 금지 태그 `script|object|embed|form|input|meta|link|base`, `on*=` 이벤트 속성, `javascript:|vbscript:|data:` URL 차단
- iframe은 **https + `youtube.com`/`www.youtube.com`/`youtube-nocookie.com`/`www.youtube-nocookie.com` + `/embed/` 경로**만 허용
- 대표이미지 URL은 동영상 리소스 패턴(`/uploads/videos/`, `.mp4|.webm|.ogg|.mov|.mkv|.avi`) 배제, `javascript:|vbscript:|data:|blob:|file:` 및 `//` 시작 차단
- 카로셀 날짜는 `YYYY-MM-DD HH:mm` 형식 + 실제 유효 날짜 검증, `inCarousel=true`면 시작·종료 모두 필수 + 시작 ≤ 종료
- validator 3종: `createPostValidators`(임시저장 허용, 카테고리 필수), `updatePostValidators`(카테고리 선택), `createPostAsUserValidators`(임시저장 불허, 작성자 필수)
- 미디어 판정 헬퍼: `containsPostMedia`, `hasAddedPostMedia`

**`categoryUploadPermission.ts` (51줄)** — `requireCategoryUploadPermission`. 미인증 401, `role==='admin'` 즉시 통과, `req.query.category_id ?? categoryId` 정수 검증 → `board_categories` `is_active` 확인 → `permissionService.checkPermission(userId, categoryId, 'canUpload')`. **multer보다 앞에 배치해 권한 거부 파일이 디스크에 기록되지 않게 설계**되었습니다.

**`caseConverter.ts` (24줄)** — `requestCaseConverter`는 body만 `keysToCamel` 처리합니다. Express 5.x에서 `req.query`는 getter-only이므로 미변환이며, 컨트롤러가 `getQueryParam`으로 양쪽 케이스를 흡수합니다(주석 명시).

### 4.6 권한 판정 `services/permissionService.ts`

권한 8종: `canRead`, `canWrite`, `canEdit`, `canDelete`, `canComment`, `canEditComment`, `canDeleteComment`, `canUpload`.

`resolveGradeId(userId)`는 `users.grade_id`와 `role`을 조회하고, **`role==='admin'`이면 `member_grades`의 `is_active=true AND is_admin=true` 등급으로 승격**합니다.

`getUserPermissions(userId, categoryId)`는 등급이 없으면 하드코딩 기본값(`canRead:true`, `canComment:true`, 나머지 false)을 반환하고, 등급이 있으면 단일 쿼리 3단 폴백을 수행합니다.

```sql
SELECT COALESCE(gcp.can_X, mg.can_X, <SQL기본값>) AS can_X
FROM member_grades mg
LEFT JOIN grade_category_permissions gcp
    ON gcp.grade_id = mg.id AND gcp.category_id = $2
WHERE mg.id = $1
```

해석 순서는 ① 등급×카테고리 개별 설정 → ② 등급 기본 권한 → ③ 하드코딩 기본값입니다. SQL 기본값은 `can_read`/`can_comment`만 true입니다. **이 해석 순서는 `controllers/auth/permissionController.ts`와 반드시 동일하게 유지**해야 하며(주석 명시), 어긋나면 "버튼은 활성인데 저장은 실패"하는 불일치가 발생합니다.

그 외 메서드: `getWritableCategories`, `getUnreadableCategoryIds`(목록 필터용), `checkPermission`, `isAdmin`, `canManagePost`(관리자 또는 `author_id` 일치), `canManageComment`.

### 6.1 마이그레이션 현황

`backend/database/migrations/` — **총 81개** `.js` 파일. 타임스탬프 범위 `1764561813485` ~ `1786100000000`. 베이스라인 `1764561813485_initial-baseline.js`는 `up`/`down`이 빈 함수입니다(기존 운영 DB 위에 얹힌 구조). 타임스탬프 중복 2쌍(`1785400000000`, `1785500000000`)이 존재하며 `--no-check-order`로 통과합니다.

**`backend/database/run-migrate.js` 동작**

1. `dotenv.config()`
2. `DATABASE_URL`이 있으면 사용, 없으면 `DB_*`로 조립. **비밀번호는 `encodeURIComponent()` 처리**. 기본값 `postgres`/`localhost`/`5432`/`aoid_db`
3. 실행 명령: `npx node-pg-migrate -m database/migrations --no-check-order {action} {extraArgs}` — **AGENTS.md의 `npx` 사용 수칙 준수**
4. 로그에서 비밀번호를 `:******@`로 마스킹
5. `execSync`, `stdio:'inherit'`, `env`에 `DATABASE_URL` 주입, 실패 시 `exit(1)`

`package.json` 스크립트: `db:migrate`(up), `db:migrate:down`, `db:migrate:redo`는 모두 `run-migrate.js` 경유. `db:migrate:create`만 `node-pg-migrate` 직접 호출(유일하게 `npx` 없음).

### 7.4 API 레이어 `src/services/` (19파일)

**`apiClient.ts`(71줄)** — `baseURL = ${REACT_APP_API_URL||''}/api`, `withCredentials: true`. 인터셉터 3단:

1. 요청 #1 — `FormData`면 `Content-Type` 헤더 삭제(브라우저 자동 설정)
2. 응답 — 성공 시 `response.data = keysToCamel(...)` (**snake → camel 자동**). 401 시 `/auth/me` 요청은 리다이렉트 없이 reject, `['/login','/register','/auth/callback','/verify-email']` 경로면 무동작, 그 외에는 `POST /api/auth/logout` 호출 후 `window.location.href='/login'`
3. 요청 #2 — FormData가 아니면 `config.data`/`config.params`에 `keysToSnake` (**camel → snake 자동**)

**토큰 주입 코드가 없습니다.** Authorization 헤더 설정이나 localStorage 접근이 전무하며, 인증은 httpOnly 쿠키 + `withCredentials`로만 이루어집니다. AGENTS.md의 "요청 인터셉터: localStorage/쿠키에서 JWT 토큰을 자동으로 Authorization 헤더에 추가" 서술은 현재 코드와 다릅니다.

진입점이 2개입니다. `api.ts`(하위호환, `sectionAPI` 포함)와 `index.ts`(권장, payment·cart·devcoins·shop `export *` + purchaseAdminAPI, **`sectionAPI` 누락**).

### 8.1 단일 소스 — `frontend/src/utils/viewport.ts` (241줄)

경계값의 유일한 정의처입니다. 파일 상단 주석에 "이 파일이 프로젝트의 유일한 구간 경계 정의다. 페이지나 컴포넌트에서 임의의 미디어 쿼리나 MUI 기본 브레이크포인트(sm=600, md=900 등)로 구간을 다시 판정하면 경계가 어긋나므로, 반드시 여기의 상수와 헬퍼만 사용한다"고 명시되어 있습니다.

```ts
VIEWPORT_BREAKPOINTS = { hd: 768, fhd: 1280, qhd: 1920, uhd: 2560, ufhd: 3840 }

VIEWPORT_RANGES = {
  mobile: { min: 0,    max: 767  },
  hd:     { min: 768,  max: 1279 },
  fhd:    { min: 1280, max: 1919 },
  qhd:    { min: 1920, max: 2559 },
  uhd:    { min: 2560, max: 3839 },
  ufhd:   { min: 3840, max: null },
}
```

**`VIEWPORT_MEDIA_QUERY`는 Media Queries Level 4 범위 문법**을 사용합니다. `(768px <= width) and (width < 1280px)` 형태이므로 소수 CSS 픽셀에서도 구간 사이에 공백이나 중복이 발생하지 않습니다.

파생 상수와 헬퍼:

| 이름 | 용도 |
| :--- | :--- |
| `VIEWPORT_MEDIA_ONLY` | 특정 구간에만 적용하는 sx 키 |
| `VIEWPORT_MEDIA_UP` | mobile 기본값 + 상위 구간 순차 덮어쓰기용 `min-width` 키 |
| `VIEWPORT_ORDER` / `VIEWPORT_UP_ORDER` | 구간 순회 순서 |
| `ViewportScale<T> = Record<AppViewport, T>` | **6구간 누락을 타입 단계에서 차단** |

| `viewportUpSx(fragments)` | 구간별 sx 조각을 캐스케이드 단일 객체로 병합 |

`mergeViewportSx`가 필요한 이유가 주석에 명시되어 있습니다. 헬퍼들이 모두 동일한 `@media (min-width: ...)` 키를 만들기 때문에 객체 스프레드로 나열하면 뒤쪽 조각이 앞쪽 조각의 미디어 블록을 통째로 덮어써 앞쪽 속성이 mobile 값만 남고 사라집니다. **두 개 이상을 함께 쓸 때는 반드시 이 함수로 병합해야 합니다.**

`useElementViewport`가 별도로 존재하는 이유도 주석에 있습니다. 같은 컴포넌트가 전체 폭 페이지와 좁은 본문 컬럼(예: 게시글 상세 하단 목록) 양쪽에서 재사용되므로, 뷰포트로만 판정하면 2560px 화면의 800px 컬럼에 UHD 밀도가 적용되어 레이아웃이 깨집니다. 경계값은 동일한 `VIEWPORT_BREAKPOINTS`를 사용하므로 기준은 하나로 유지됩니다. 구간이 바뀔 때만 상태를 갱신하여 스크롤바 토글 같은 미세 폭 변화로 리렌더되지 않습니다.

### 9.2 채점 알고리즘

**삼각검사 — 무게중심 좌표(Barycentric) 환산** (`triangleTestController.ts:6-49`)

```
SQRT3_DIV2 = √3 / 2

λA = y / SQRT3_DIV2
λC = x - y / (2 · SQRT3_DIV2)
λB = 1 - λA - λC

각 λ를 [0, 1]로 clamp
sum = λA + λB + λC
  sum > 0  → 각 λ /= sum
  sum == 0 → 모두 1/3

scoreX = round(λX × 10000)
합이 10000이 아니면 diff(= 10000 - 합)를 최댓값 성향에 가산
```

집계는 조회 시점에 재계산합니다(`getSubmissionResult`, `triangleTestController.ts:813~`).

```
성향별 합계   : 문항의 option_{a,b,c}_trait_id에 대응하는 score_{a,b,c}를 누적 (880-897)
totalPossible = (답변 수 || 1) × 10000                        (912)
percentage    = (scoreSum / totalPossible) × 100, 소수 1자리    (915)
mean          = round(해당 성향 점수 리스트 합 / count)         (0~10000 정수)
stdDev        = round(sqrt( Σ(v - mean)² / count ))            (930, 모집단 분산)
```

**선다형검사 — 가중치 합산 후 기여도 백분율** (`multipleChoiceTestController.ts:544-618`)

```
성향별 합계     : 선택된 옵션들의 score_weights를 순회해 traitScores[traitId] += score
totalScoreSum   = Σ 모든 성향 점수                                (599)
percentage      = round( (score / totalScoreSum) × 100 × 10 ) / 10  (608)
dominantTraitId = percentage 최댓값 성향                           (610-613)
```

정리하면 삼각은 **문항 수 × 10,000점을 분모로 쓰는 절대 비율**, 선다형은 **획득 총점 대비 상대 기여도**입니다. 삼각은 문항별 평균과 표준편차까지 산출합니다.

주의할 구조적 특성: 삼각 `percentage`의 분모가 "전체 문항 수 × 10000"이므로 특정 성향이 일부 문항의 꼭지점에만 배정되면 그 성향의 percentage는 구조적으로 낮게 나옵니다. 반면 `mean`은 해당 성향이 등장한 문항만으로 평균을 냅니다. 결과지 매칭은 `mean` 기반, 종합분석 정렬은 `percentage` 기반이라 두 기준이 혼용됩니다.

### 9.3 결과 산출 5단 파이프라인

두 컨트롤러의 `getSubmissionResult`(triangle 813~1203, mc 660~999)가 동일 구조를 따릅니다.

**(1) 성향 점수 산출** — 응답은 `traitScores[]` 배열(`traitId`, `name`, `alias`, `description`, `additionalInfo`, `imageUrl`, `score`, `percentage`, 삼각은 추가로 `maxBaseScore`, `mean`, `stdDev`, `count`, `scores[]`).

**(2) 결과지(results) 구간 매칭** — `{min_value, min_operator, max_value, max_operator}` 4-튜플. 연산자는 `>=`/`>`, `<=`/`<`만 취급하고 그 외는 `>=`/`<=`로 폴백합니다.

| 검사 | 비교 대상 값 | 위치 |
| :--- | :--- | :--- |
| 삼각 | `meanScorePct = (mean > 0) ? (mean / 100).toFixed(1) : percentage` → 0~100 스케일 | `triangleTestController.ts:970` |
| 선다형 | `val = ts.score` → **원점수 합** (백분율 아님) | `multipleChoiceTestController.ts:788` |

매칭 절차:
1. 해당 성향의 결과지를 `min_value` 오름차순 정렬
2. `minCond && maxCond`를 만족하는 **첫 구간**을 채택하고 `break`(중복 방지)
3. 어느 구간도 맞지 않으면 **스마트 폴백**: 각 구간 중앙값 `(min+max)/2`과의 절대 편차가 최소인 구간을 강제 채택 (triangle 1005-1020, mc 819-835)

즉 결과지가 1개 이상 등록되어 있으면 매칭은 **항상 성공**하고, 구간이 비어 있으면 그 성향은 `matchedResults`에서 누락됩니다.

**(3) 전체 참여자 분포 통계**
- 선다형: `dominant_trait_id` 기준 단순 `GROUP BY` 빈도 (mc 838-857)
- 삼각: `dominant_trait_id` 컬럼이 없으므로 CTE로 전 제출 재집계 — `submission_trait_scores` → `ranked_scores(ROW_NUMBER() OVER (... ORDER BY score_sum DESC, trait_id ASC))` → `rn=1`만 집계 (triangle 1024-1063)

**(4) 종합분석(overall) 매칭** — `overall_display_type` 분기 (9.4절)

**(5) 최선/최악(best_worst) 조합키 생성**

```
대상   = traitScores 중 selected_overall_trait_ids에 포함된 성향만
정렬   = percentage 내림차순, 동점이면 traitId 오름차순
best   = 정렬 첫 번째 traitId
worst  = 정렬 마지막 traitId
combinationKey = `${bestId}_${worstId}`        (triangle 1143, mc 933)
```

관리자 측 조합 생성(`generateBestWorstCombinations`, triangle 2089 / mc 1488)도 순서쌍 전수를 `bestId_worstId`로 만들므로 읽기/쓰기 키 규칙이 일치합니다.

### 9.4 `overall_display_type` 3종

값은 `'none' | 'sequence' | 'best_worst'`입니다. 화이트리스트는 서버(`updateOverallDisplayType`: triangle 1865-1878, mc 1264-1277)와 프론트 타입(`frontend/src/types/index.ts:865`) 양쪽에 있고 목록 밖의 값은 `'none'`으로 강제됩니다. 컬럼은 `VARCHAR(50) NOT NULL DEFAULT 'none'`(마이그레이션 `1785300000000`).

| 값 | 조회 동작 | 조회 테이블 | 필요 조건 |
| :--- | :--- | :--- | :--- |
| `none` | 무조건 `{type:'default', imageUrl: default_overall_image_url, descriptionSets: default_overall_description_sets}` | 없음(시트 컬럼 직접) | — |
| `sequence` | 대상 성향을 percentage 내림차순(동점 traitId 오름차순) 정렬 → 조합키 조회 | `*_overall_results` | `selected_overall_trait_ids.length > 0` |
| `best_worst` | best/worst 2개 추출 → 조합키 조회 | `*_best_worst_results` | `selected_overall_trait_ids.length >= 2` **그리고** 매칭된 `targetScores.length >= 2` |

공통 폴백: 조합 레코드가 없거나, 있어도 `representativeImageUrl`·`representativeImageTitle`·`descriptionSets`(비어있지 않은 배열) 중 **아무것도 없으면** `type:'default'`로 되돌립니다(`hasContent` 검사, triangle 1106/1155, mc 896/945).

응답 형태:

```ts
{ type: 'default' | 'sequence' | 'best_worst',
  combinationKey?: string,       // default 모드에서는 없음
  imageUrl, imageTitle?, descriptionSets }
```

`common_overall_description`은 표시 모드와 무관하게 시트 컬럼에서 그대로 전달되어 결과지 2페이지 그래프 아래 공통 주석으로 출력됩니다.

### 9.5 진행상황(progress) / UUID 하이브리드 / 공개 전환

**progress 저장** — `triangle_test_progress`(복합 PK `user_id, test_id`, 마이그레이션 `1783470000000`), `multiple_choice_test_progress`(`UNIQUE(user_id, test_id)`). 저장은 `INSERT ... ON CONFLICT (user_id, test_id) DO UPDATE` 업서트(triangle `saveTestProgress:1628`, mc `saveProgress:520`)이며 `answers`는 JSONB, `current_index`는 정수입니다.

삼각 프론트는 문항 이동 시 즉시 저장 + `answers`/`currentIdx` 변경 시 1.5초 디바운스 저장 두 경로를 둡니다. 선다형은 디바운스 없이 보기 선택(`handleSelectOption`)과 문항 이동(`handleNavIndex`) 시마다 저장합니다.

복원 시 무결성 검증이 있습니다. 저장된 모든 questionId가 현재 문항 목록에 존재하는지, 문항에 연결된 성향이 유실되지 않았는지 검사하고, 실패하면 "시트 성향 또는 질문 구성이 변경되어..." 토스트와 함께 진행 내역을 초기화합니다. URL 쿼리로 프롬프트를 우회할 수 있습니다(`?resume=true` 확인창 없이 이어서, `?reset=true` 새로 시작). 제출 성공 시 같은 트랜잭션에서 progress 행을 `DELETE`합니다(triangle 797-801, mc 625-628).

**UUID vs id 하이브리드** — `submissions` 테이블에 `uuid`(마이그레이션 `1785100000000`, `pgcrypto` + `gen_random_uuid()`)와 `id`가 공존합니다. 제출 시 `INSERT ... RETURNING id, uuid`로 둘 다 확보합니다.

판별 로직은 정규식 1개로 통일되어 있습니다.

```ts
const isUuid = /^[0-9a-fA-F]{8}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{12}$/.test(submissionId);
// true  → WHERE s.uuid = $1
// false → WHERE s.id   = $1
```

적용 위치: `getSubmissionResult`(triangle 818, mc 665), `updateSubmissionPublic`(triangle 1215, mc 1008). 조회 후 `const actualSubId = submission.id`로 숫자 ID를 뽑아 하위 쿼리에 사용합니다.

프론트도 대칭 처리합니다(`TriangleTestResultPage.tsx:84`, `MultipleChoiceTestResultPage.tsx:104`).

```ts
const subId = submissionId && /^\d+$/.test(submissionId)
  ? parseInt(submissionId, 10)
  : (submissionId || '');
```

제출 직후 이동은 UUID를 우선합니다(`res.data.uuid || res.data.submissionId`). 즉 공유 링크는 UUID, 레거시 링크는 숫자 ID로 모두 열립니다.

**공개(is_public) 전환** — 컬럼은 마이그레이션 `1785500000000`에서 두 submissions 테이블에 추가되었습니다. 조회 권한은 `isOwnerOrAdmin = (userId && submission.user_id === userId) || userRole === 'admin'`이며 `!isPublic && !isOwnerOrAdmin`이면 403(triangle 836-840, mc 756-760)입니다. 응답에 `canEditAccess: isOwnerOrAdmin`을 실어 프론트 토글 노출을 제어합니다. 라우트가 `optionalAuthenticate`이므로 공개 리포트는 비로그인도 열립니다. 전환은 `PUT /submissions/:submissionId/public`(`authenticate` 필요)이고 본인/관리자가 아니면 403입니다. 비공개 시 프론트가 `<meta name="robots" content="noindex, nofollow">`를 렌더합니다.

### 9.6 결과 리포트 페이지 구조 (AGENTS.md 캡처 수칙 준수 확인)

**`PrintPage.tsx`(495줄)의 두 판형 변형**

- `variant="a4"`(기본): 폭 800px / 높이 1130px **고정**(`DEV_SPECTRUM_REPORT_PAGE`), 내부 패딩 32px, `overflow: hidden`. CSS `zoom`으로 레이아웃 전체를 정비율 스케일
- `variant="flow"`: 유동폭·자동높이 카드. 줌을 걸지 않아 좁은 화면에서 원본 글자 크기 유지. 화면 전용이며 캡처 대상이 아님

**줌 투 핏 계산** (`PrintPage.tsx:130-168`)

```
fitZoom = wrapper.clientWidth / DEV_SPECTRUM_REPORT_PAGE.baseWidth       (144)
maxZoom = DEV_SPECTRUM_REPORT_LAYOUT.maxPageZoom[getDevSpectrumViewport(window.innerWidth)]  (149)
zoom    = max( min(fitZoom, maxZoom), 0.1 )  → round(x * 1000) / 1000
```

`fitZoom`을 넘지 않으므로 어떤 구간에서도 가로 스크롤이나 잘림이 생기지 않고, `maxPageZoom`이 QHD 1.15 / UHD 1.35 / UFHD 1.6이라 넓은 화면에서는 판형을 정비율 확대해 여백을 줄입니다. 재계산 트리거는 최초 1회 + `resize` + `orientationchange` + wrapper `ResizeObserver`입니다. `window.matchMedia('print').matches`이거나 `forceZoomOne`/flow면 줌을 1로 고정합니다.

머리말/꼬리말은 a4에서 `position: absolute`로 네 귀퉁이에 고정합니다(브랜드 마크, 응답자 아바타·이름·제출일, `Page N / M`, 조회일시, 분석결과 고유번호=UUID). flow에서는 자연 흐름 + 줄바꿈 허용으로 분기합니다.

관리자 입력에 공백 없는 긴 문자열이 들어와도 판형 폭을 밀어내지 않도록 페이지 내부에 `'& .MuiTypography-root': { minWidth: 0, maxWidth: '100%', overflowWrap: 'anywhere' }`와 `.MuiChip-label` 말줄임 처리를 두었습니다.

`fixedRatio` prop은 **현재 판형에 반영되지 않습니다.** 주석(`PrintPage.tsx:88-93`)에 "페이지별 높이 가변 옵션을 위해 예약되어 있으며, 아직 판형에 반영되지 않습니다"로 명시되어 있고, 두 결과 페이지가 3페이지에 `fixedRatio={false}`를 넘기지만 동작 차이는 없습니다.

**페이지 구성 (두 검사 동일하게 A4 3장)** — `renderA4Pages(idPrefix, forceZoomOne)`(TriangleTestResultPage 736 / MultipleChoiceTestResultPage 720)

| 페이지 | 내용 |
| :--- | :--- |
| 1 | 리포트 타이틀(그라데이션 스티커) → 대표 성향 진단 결과(성향명·정의/설명, 폴라로이드 스타일 대표 이미지 5deg 회전 + 구름형 SVG 배경 `viewBox="0 0 240 240"`, 별칭, `additional_info`) → 전체 참여자 성향 분포 바 |
| 2 | 종합 성향 분석: 좌상단 조합 대표 이미지(-6deg, 타이틀 라벨) + `MultipleChoiceRadialChart` 방사형 그래프 + 범례/점수 표 → `common_overall_description` 공통 주석 → `overallAnalysis.descriptionSets` 해설 카드 목록 |
| 3 | 성향별 세부결과: percentage 내림차순 정렬된 `matchedResults` 카드 나열. 성향 칩 + 점수 게이지 + 결과 본문 + 우측 결과 이미지 + `TraitOutcomeDotTrack`(N분위 트랙) |

검사별 차이: 삼각은 `TriangleScoreGaugeBar`(평균 ± 표준편차 구간 표시)와 `평균: N점 (±M)` 문구, 선다형은 `ScoreStamp`(Caveat 폰트 도장)를 카드 우상단에 배치합니다.

좁은 구간(mobile/HD)은 A4 대신 `narrowPages: React.ReactNode[][]`로 재구성합니다. 3장 고정을 유지하면서 각 장을 섹션 배열로 쪼개 단일 카드에 `Divider`로 구분하며, "몇 페이지의 몇 번째"라는 의미를 데스크탑과 일치시키기 위해 `screenPageCount = 3`으로 고정합니다.

네비게이션은 `IntersectionObserver`(`rootMargin: '-30% 0px -35% 0px'`, `threshold: 0.15`)로 `report-page-N` 요소를 감시해 활성 페이지를 추적하고, `scrollToPage`가 `DEV_SPECTRUM_REPORT_NARROW.scrollOffset[viewport]`만큼 여유를 두고 스무스 스크롤합니다.

### 9.7 PDF 저장 / 이미지 복사 파이프라인

캡처 대상은 **항상 오프스크린 A4 스테이지**입니다. `useReportCaptureStage({ useOffscreen: true, screenRootId: 'report-paper', stageId: 'report-capture-stage' })`가 저장 시점에만 `<ReportCaptureStage>`를 마운트하고 거기에 `renderA4Pages('capture-page', true)`를 렌더합니다.

`ReportCaptureStage.tsx`는 `display:none`이 아니라 `position: fixed; left: -100000px; zIndex: -1; pointerEvents: none`으로 밀어냅니다(html2canvas가 크기를 측정해야 하므로). 폭을 `baseWidth`(800px)로 확보하고 자식 `.print-page-wrapper`의 `marginBottom`을 `0 !important`로 죽여 페이지가 빈틈없이 이어지게 합니다. 마운트 완료는 `mountResolverRef` + `requestAnimationFrame` 2프레임 대기로 보장합니다.

`reportCapture.ts`(201줄) 파이프라인:

1. **스크립트 지연 로드** — html2canvas 1.4.1 / jsPDF 2.5.1을 cdnjs에서 `loadScriptOnce`로 로드 (22-40행). **외부 CDN 런타임 의존**
2. `waitForFonts()`(document.fonts.ready, 4초 타임아웃) + `waitForImages()`(미완료 img의 load/error, 8초 타임아웃)
3. **`forceZoomOne(root)`** — html2canvas가 CSS `zoom`을 해석하지 못하므로 `.print-page` 전부에 `zoom: 1 !important`를 강제하고 스냅샷을 보관, `finally`에서 `restoreZoom`으로 복원 (56-76행)
4. `captureCanvas` — `{ scale: 2, useCORS: true, backgroundColor: '#ffffff', logging: false, scrollX: 0, scrollY: 0, windowWidth: 850 }`

산출물:

- **`copyReportImage(root, fileName)`** — 루트 전체를 PNG 1장으로 캡처 → `ClipboardItem`으로 클립보드 write. 실패 시 `<a download>` 파일 다운로드 폴백. `{ copiedToClipboard: boolean }` 반환
- **`saveReportPdf(root, fileName, { onProgress })`** — `getPrintPages(root)`로 `.print-page` 목록을 얻어 페이지별 캡처, JPEG 0.95로 A4 세로(210×297mm)에 삽입. `imgHeight = canvas.height × 210 / canvas.width`로 종횡비 유지, `imgHeight > 297+1`이면 음수 y 오프셋으로 여러 PDF 페이지에 분할하는 방어 로직 포함. `onProgress(current, total)`는 토스트 진행률로 연결

두 결과 페이지는 인쇄용 `<style>@media print</style>`도 인라인으로 넣어 header/footer/`.no-print`/button/a를 숨기고 `.print-page-wrapper { margin: 0 !important }`로 6구간 외곽 여백을 리셋합니다.

### 9.9 인트로 페이지 (`SpectrumIntroPanel`)

`/dev-spectrum/intro/:slug`는 `TriangleTestListPage`로 라우팅되고, 그 안에서 `DevSpectrumShell`의 `activeSection='intro'`일 때 `SpectrumIntroPanel`(2,031줄)을 우측 콘텐츠 영역에 렌더합니다. `pages/SpectrumIntroPage.tsx`(762줄)도 같은 API를 쓰는 독립 페이지 형태로 존재하지만 **`App.tsx` 라우트 테이블에 등록되어 있지 않습니다.**

`DevSpectrumShell`의 섹션은 `'dashboard' | 'tests' | 'results' | 'intro'` 4종이며 상단 3개만 primary 내비게이션에 노출됩니다.

역할은 검사 응시 전 "무엇을 측정하고 어떤 결과가 나오는지"를 보여주는 카탈로그 겸 진입점입니다.

- 헤더 배너 — 카테고리 칩, 타입 칩(삼각/선다형), 비활성 칩, 제목·설명, 표지 이미지(FHD 이상 `grid-template-columns: minmax(0,1fr) 280~400px`)
- 검사대상성향 카로셀 — 1:1 정사각 카드, 좌상단 alias 칩 + 성향명
- 성향별 결과지 카로셀 — `resultsByTrait`로 성향 단위 그룹핑
- 종합분석 조합 앨범 — `overallResults` / `bestWorstResults`
- 액션 버튼 — `onStart`, `onResume`, `onLatestResult`, `onBack`. 활성/비활성 판정은 호출부에서 응시 완료 여부, 재응시 잔여 시간, 등급 접근 권한, 진행 내역 유무, 최근 제출 유무를 계산해 prop으로 내려줍니다. `startAriaLabel`도 `참여 완료`/`Nh 후 가능`/`참여 권한 없음`으로 분기
- **획득 스탬프** — `userAcquiredInfo`로 이미 받은 성향/결과지/조합 카드에 도장을 겹쳐 표시

데이터 소스는 단일 엔드포인트 `GET /api/dev-spectrum/intro/:slug`(`optionalAuthenticate`) → `introController.getTestIntroBySlug`(382줄)입니다. 프론트 호출은 `multipleChoiceTestAPI.getTestIntroBySlug(slug)`이지만 **서버가 슬러그로 검사 종류를 자동 판별**합니다(`multiple_choice_tests` 먼저 조회 → 없으면 `triangle_tests`). 이후 종류에 맞는 4개 컬렉션을 로드해 한 응답으로 합칩니다.

```
응답: { testType, test{...}, traits[], results[], overallResults[], bestWorstResults[], userAcquiredInfo }
```

로그인 사용자면 최근 제출 1건(`ORDER BY submitted_at DESC LIMIT 1`)을 읽어 성향 점수를 **다시 채점**하고 결과지 구간 매칭(`acquiredResultIds`)과 조합 매칭(`acquiredOverallId`, `acquiredCombinationKey`)을 계산합니다. 이 블록 전체가 try/catch로 감싸져 있어 실패 시 `userAcquiredInfo`는 `null`이 되고 페이지는 정상 렌더됩니다.

**비대칭 지점 2곳**

1. `triangle_test_results`는 `test_id`와 `trait_id`를 모두 가지지만 `multiple_choice_test_results`는 `trait_id`만 가집니다. 그래서 선다형 결과지 조회는 항상 `JOIN multiple_choice_test_traits ON r.trait_id = t.id WHERE t.test_id = $1`로 우회합니다(mc 310-324).
2. `multiple_choice_test_submissions`에는 `dominant_trait_id`가 있으나 `triangle_test_submissions`에는 없어, 삼각의 분포 통계는 매번 CTE 재집계가 필요합니다.

3. **하위 3탭**
   - `기본값설정`: `default_overall_image_url` + `default_overall_description_sets`(모든 폴백 경로가 쓰는 값)
   - `순차조합설정 (N)`: 1단계 성향 체크(`selected_overall_trait_ids`) → 2단계 `순차 조합 일괄 생성`(순열 전수) / 전체 일괄 저장 / **CSV 다운로드·업로드** / 조합 전체 삭제. 50개 단위 `Pagination`
   - `최선최하조합설정 (N)`: 동일 흐름의 `bestId_worstId` 순서쌍 전수 생성/저장/CSV/삭제(최소 2개 성향 필요)

조합 카드에는 1-based 성향 순번으로 만든 표시용 조합키(`1_2_3`)와 `1.성향A → 2.성향B` 조합명, 대표 이미지 업로더, `DescriptionSetEditor`(라벨+설명 세트 N개)가 들어갑니다. 정렬은 `compareSeqKeys` 자연 정렬(`1_2` < `1_10`)입니다.

CSV 파이프라인이 견고하게 작성되어 있습니다. BOM(`\uFEFF`) 부착, `,`/`\t`/`;` 구분자 자동 감지, 따옴표 이스케이프 파서 직접 구현, `normalizeKey`로 엑셀 서식(`="1_2"`, `1-2`, `1 2`, `1.2`)을 모두 `1_2`로 정규화합니다.

주의: 카드에 표시되는 조합키는 **1-based 순번** 기반이고 DB `combination_key`는 **trait_id** 기반이므로 두 값은 일반적으로 다릅니다. CSV 왕복 매칭은 `normalizeKey(item.combinationKey || traitIds.join('_'))`로 수행합니다(356, 442, 505, 590행).

### 11.3 Nginx (`nginx/aoid_v2_260726.conf`)

실제 서버 반영 경로는 **`/etc/nginx/sites-available/aoid`**이고 이 폴더는 배포 시점별 사본입니다. `aoid_v1_260725.conf`는 이전 버전, `aoid_v2_260726.conf`가 최신(v1 + 데브스펙트럼 SEO 라우팅 + uploads CORS/캐시 헤더)입니다.

**봇 감지 맵**

```nginx
map $http_user_agent $is_bot {
    default 0;
    ~*(google-inspectiontool|googlebot|bingbot|yeti|daum|naverbot|
       facebookexternalhit|twitterbot|kakaotalk-scrap|linkedinbot) 1;
}
```

**서버 블록 2개**
- 443 SSL — `server_name aoid.kr www.aoid.kr`, `client_max_body_size 50M`, Certbot 인증서(`/etc/letsencrypt/live/aoid.kr/`), `options-ssl-nginx.conf` + `ssl-dhparams.pem` include
- 80 — `aoid.kr`/`www.aoid.kr` → 301 HTTPS 리다이렉트 후 `return 404`(Certbot). 점검 모드 블록이 중복 정의되어 있으나 `return 404`가 앞서 실효 없음

**점검 모드 스위치 (배포 락 기반 503)**

```nginx
set $m_mode 0;
if (-f /var/www/html/frontend_deploy.lock) { set $m_mode 1; }
if (-f /var/www/html/backend_deploy.lock)  { set $m_mode 1; }
if ($uri = /maintenance.html) { set $m_mode 0; }   # 점검 페이지 예외
if ($m_mode = 1) { return 503; }
error_page 503 /maintenance.html;
location = /maintenance.html { root /var/www/html; }
```

프론트/백 락 중 하나만 있어도 전체 503입니다.

**라우팅**

| location | 처리 |
| :--- | :--- |
| `/` | `try_files $uri $uri/ /index.html` (SPA), `root /var/www/html` |
| `/api` | `proxy_pass http://localhost:5000`, HTTP/1.1 + Upgrade/Connection, `X-Real-IP`/`X-Forwarded-For`/`X-Forwarded-Proto`, `proxy_cache_bypass $http_upgrade` |
| `= /sitemap.xml` | `proxy_pass http://localhost:5000/api/sitemap.xml` (동적 sitemap) |
| `/uploads` | 백엔드 5000 프록시 + `Access-Control-Allow-Origin "*"` + `Cache-Control "public, max-age=86400"` (트위터/카카오 스크랩 봇 이미지 접근용, **유일한 캐시 설정**) |

**봇 분기 SEO 프록시 3종**

```nginx
# 게시글
location ~* ^/(board|[a-zA-Z0-9_-]+)/([0-9]+)$ {
    if ($is_bot = 1) { rewrite ... /seo/$1/$2 break; proxy_pass http://localhost:5000; }
    root /var/www/aoid/frontend/build;
    try_files $uri $uri/ /index.html;
}

# 데브스펙트럼 결과 (v2 추가)
location ~* ^/dev-spectrum/(triangle-test|multiple-choice)/result/([^/]+)$ { ... /seo/dev-spectrum/$1/result/$2 ... }

# 레거시 결과 경로 (v2 추가)
location ~* ^/(triangle-test|multiple-choice)/result/([^/]+)$ { ... /seo/$1/result/$2 ... }
```

이 3개 블록만 `root`가 `/var/www/aoid/frontend/build`로 서버 기본값(`/var/www/html`)과 다릅니다.

## 14. 코드 실독으로 확인된 정합성 이슈

작업 시 걸릴 가능성이 높은 순서로 정리했습니다. **모두 정적 코드 확인 기반이며, 별도 표기가 없는 항목은 런타임 실행으로 검증하지 않았습니다.**

### 14.1 [최우선] 순차조합(sequence) 조합키 구분자 불일치 — grep으로 직접 확인

생성·저장은 언더바(`_`), 조회는 하이픈(`-`)을 사용합니다.

```
생성/저장 (join('_'))
  triangleTestController.ts       : 1906, 1977, 1984, 2032, 2250
  multipleChoiceTestController.ts : 1305, 1376, 1383, 1431, 1639

조회 (join('-'))
  triangleTestController.ts       : 1096
  multipleChoiceTestController.ts : 886
  seoService.ts                   : 242, 308
```

`combination_key`에는 `UNIQUE(test_id, combination_key)` 제약이 있고 생성기가 `_` 키만 저장하므로, `overall_display_type='sequence'`인 시트는 결과 조회 시 매칭에 실패해 항상 `type:'default'` 폴백으로 떨어집니다. 관리자 UI(`OverallAnalysisTab.tsx`)의 `normalizeKey`도 하이픈을 언더바로 통일하므로 프론트에서 하이픈 키를 만들어 보낼 경로는 없습니다.

`best_worst`는 양쪽 모두 `${bestId}_${worstId}`를 쓰므로 정상입니다(triangle 1143·2117, mc 933·1516, seoService 259).

**수정 방향**: 조회 측 3곳을 `join('_')`으로 통일하는 것이 최소 변경입니다(기존 저장 데이터를 건드리지 않음).

### 14.2 [높음] 선다형 응시 제한 미적용

`allowed_grade_ids`, `attempt_limit_type`, `attempt_interval_hours`를 저장·수정만 하고(`multipleChoiceTestController.ts` 44-46, 79-81), `getTestByIdOrSlug`(435)와 `submitTest`(544)에서 검증하지 않습니다. 삼각은 `checkTestEligibility`(`triangleTestController.ts:254`)로 조회·제출 양쪽에서 검증합니다. 관리자가 선다형 시트에 등급 제한이나 1회 응시 제한을 걸어도 실효가 없습니다.

### 14.3 [높음] 마이그레이션 체인 밖 스키마 정의

`npm run db:migrate`만으로는 아래 테이블이 생성되지 않습니다.

- `site_settings`, `header`, `quick_boxes`, `notice_boxes`, `program_boxes`, `member_app_boxes`, `business_items` → `backend/scripts/db-migrations/*.ts`에만 정의
- `orders`, `payments`, `payment_history`, `subscriptions`, `shop_products`, `user_items`, `product_types`, `user_devcoins`, `devcoins_transactions`, `shopping_cart`, `app_visions` 계열, `promo_cards`, `cta_section`, `cta_activity_cards` → `backend/database/sql_migrations/*.sql`(35개)에만 정의

`settingsService`와 `pageContentController`가 `site_settings`에 의존하므로 신규 환경 구축 시 반드시 별도 실행이 필요합니다. 또한 AGENTS.md 초기 설정 절의 `psql -f backend/database/schema.sql` 경로에 파일이 없습니다(실제는 `backend/database/legacy/schema.sql`).

### 14.4 [높음] 프론트 배포 락 해제 순서

`frontend/.github/workflows/deploy.yml` 7단계에서 `rm -f frontend_deploy.lock`이 `nginx -t` **앞**에 실행됩니다. 또한 5~7단계에 `if: always()` 류 보호가 없어 6단계(scp) 실패 시 락이 남아 사이트가 503에 머물 수 있습니다. 반대로 Nginx 설정 오류가 있어도 락은 이미 해제됩니다.

### 14.5 [중간] `handleValidationErrors` 누락

validator를 통과하지 못해도 400 응답이 나가지 않는 위치입니다.

- `POST /api/admin/categories`, `PUT /api/admin/categories/:id`
- `appVisionRoutes.ts`의 `appVisionValidation` / `feedbackValidation` 적용 라우트 전체
- `adminRoutes.ts`의 댓글 대리작성(`POST /comments/post/:postId/create-as-user`)

### 14.6 [중간] 인증·권한 관련

- **JWT 검증에 DB 조회 없음** — `authenticate`가 토큰 payload의 `role`만 신뢰하므로 관리자 권한 회수나 계정 비활성화가 토큰 만료(7일)까지 반영되지 않습니다
- **`POST /api/payments/webhook`이 인증·서명 미들웨어 없이 노출** — 검증이 전적으로 `webhookController.handleWebhook` 내부 구현에 의존합니다
- **`requireEmailVerified` 미적용** — 미들웨어가 구현되어 있으나 어떤 라우트에도 붙지 않았습니다
- **`PrivateRoute` 부재** — 프론트에 로그인 필요 페이지용 라우트 가드가 없어 `/mypage`, `/cart`, `/orders`, `/payment`는 페이지 내부 처리에만 의존합니다
- **CORS origin이 단일 문자열**(`env.FRONTEND_URL`) — 다중 도메인 허용이 불가합니다

### 14.7 [중간] 업로드 제한 누락

7개 multer 업로더에 `limits`가 설정되지 않았습니다: `uploadHeroImage`, `uploadHeaderLogo`, `uploadQuickBoxIcon`, `uploadNoticeBoxThumbnail`, `uploadProgramBoxImage`, `uploadMemberAppBoxIcon`, `uploadPromoCardIcon`. 라우트의 `handleMulterError`는 크기 초과 메시지를 준비하지만 `LIMIT_FILE_SIZE`가 발생하지 않습니다.

### 14.8 [중간] 데브스펙트럼 로직 불일치

- **선다형 결과지 매칭 단위** — `ts.score`(원점수 합)를 기준으로 하므로, 관리자가 구간을 0~100 백분율로 이해하고 입력하면 항상 스마트 폴백 경로를 타게 됩니다. 삼각은 0~100 스케일(`mean/100`)을 씁니다
- **동점 시 대표성향 비결정성** — 선다형 `submitTest`의 성향 목록 조회(`multipleChoiceTestController.ts:560`)에 `ORDER BY`가 없어 동점 시 DB 반환 순서에 의존합니다
- **인트로 vs 결과 페이지 조합 판정 기준 차이** — 인트로(`introController`)는 `selected_overall_trait_ids` 필터 없이 전체 성향으로 best/worst를 뽑습니다. 결과 페이지는 선택 성향만 필터링하므로 두 화면의 조합 판정이 어긋날 수 있습니다
- **인트로의 `= ANY(trait_ids)`** — `trait_ids`는 JSONB 컬럼인데 Postgres 배열 연산자를 적용합니다. 감싸고 있는 try/catch가 오류를 흡수해 `acquiredOverallId`가 조용히 채워지지 않습니다
- **`getAdminSubmissions`(삼각, 1246) CTE 범위** — `submission_scores`/`ranked_scores` CTE에 `test_id` 필터가 없어 전체 제출을 집계한 뒤 마지막에 필터링합니다. 데이터 증가 시 비용이 커집니다
- **`saveTraitsBatch`의 keep-list SQL** — `'... id NOT IN (' + existingIds.join(',') + ')'`로 문자열 연결합니다(triangle 1760, mc 1159). 값이 DB에서 온 숫자 ID라 실질 위험은 낮지만 프로젝트 규칙(항상 파라미터화)에서 벗어납니다
- **삼각 `stdDev` 분모** — 모집단 분산(분모 `count`)입니다(triangle 928-930). 표본 표준편차가 의도라면 `count-1`이어야 합니다

### 14.9 [중간] 프론트엔드 구조 불일치

- **파라미터 리다이렉트 미치환** — `App.tsx`의 `<Navigate to="...:slug">` / `":submissionId"` 5건이 리터럴 경로로 이동합니다

- **브레이크포인트 이원화** — 6구간(`utils/viewport.ts`) vs MUI 기본(`down('md')`=900px). 테마에 breakpoints 커스터마이즈가 없습니다

## 16. 결론 및 작업 가이드

### 16.1 종합

AoID 프로젝트는 **556개 소스 파일 / 약 14.3만 라인(143,037 LoC)** 규모의 TypeScript 풀스택 웹 애플리케이션입니다(NewsMaker 제외). 3개 Git 서브모듈로 분리되어 각각 독립 배포되고, 프로덕션은 AWS EC2 + Nginx + PM2 위에서 GitHub Actions로 자동 배포됩니다.

아키텍처 측면에서 특히 정교하게 다듬어진 영역은 다음 4곳입니다.

1. **6구간 뷰포트 체계** — 경계값 단일 소스, Level 4 범위 문법, `ViewportScale<T>` 타입 강제, `mergeViewportSx` 충돌 방지, 요소 폭 기준 판정 훅까지 갖춰 재정의 여지를 구조적으로 차단
2. **리포트 캡처 파이프라인** — 화면 렌더링(유동폭/줌투핏)과 캡처 대상(오프스크린 800×1130 고정)을 분리해 기기 무관 산출물 동일성을 보장
3. **3단 권한 폴백** — 단일 쿼리 `COALESCE` 3단으로 등급×카테고리 → 등급 기본 → 하드코딩을 해석하며, 서비스와 컨트롤러의 해석 순서 동일성을 주석으로 명시
4. **미디어 업로드 권한 판정** — 미디어 참조 개수 비교로 "새 미디어 추가"만 골라내 `canUpload`를 요구하고, 표 서식 변경 오판을 막는 테스트 17케이스로 규칙을 고정

반대로 보완이 필요한 영역은 **테스트 커버리지**(백엔드 1파일, 프론트 10파일 전부 에디터 모듈)와 **스키마 정의 분산**(마이그레이션 체인 밖 테이블 다수)입니다.

### 16.2 작업 시 유의할 지점

- **케이스 변환이 양방향 자동**입니다. 새 API를 추가할 때 백엔드는 snake_case로 응답하면 되고, 프론트는 camelCase로 요청하면 됩니다. 단 `req.query`는 미변환이므로 `getQueryParam(req, 'camelKey', 'snake_key')`를 사용하세요.
- **에러 응답의 `error` 필드는 반드시 문자열**이어야 합니다. 프론트 전역이 `response.data.error`를 toast에 직접 넘깁니다.
- **뷰포트 규격을 추가할 때는** `utils/viewport.ts`의 경계값을 건드리지 말고 `boardViewport.ts` / `devSpectrumViewport.ts` 스타일로 `ViewportScale<T>` 테이블을 추가하세요. sx 조각 2개 이상을 합칠 때는 `mergeViewportSx`가 필수입니다.
- **데브스펙트럼 리포트에 콘텐츠를 추가할 때는** A4 1130px 고정 높이 + `overflow: hidden` 제약을 먼저 확인하세요. 약 1000px를 넘으면 잘립니다.
- **관리자 화면을 추가할 때는** `admin/config/menuConfig.ts`에 메뉴 항목을 등록하고 `App.tsx`의 `/admin` 중첩 라우트에 `lazy()` 컴포넌트를 추가하는 2곳 수정이 필요합니다.
- **새 테이블을 만들 때는** 반드시 `backend/database/migrations/`에 CommonJS 문법으로 작성하세요. `scripts/db-migrations/`나 `sql_migrations/`는 자동 반영되지 않습니다.

### 16.3 준비 완료

본 보고서 작성으로 프로젝트 전 영역(NewsMaker 제외)의 구조 파악을 완료했습니다. 신규 기능 개발, UI/UX 및 반응형 레이아웃 개선, 버그 수정, 백엔드 라우팅 추가, DB 스키마 변경, 인프라 설정 수정 등 모든 개발 요청을 즉시 지원할 수 있는 상태입니다. 14절의 이슈 목록은 우선순위대로 정리되어 있어 개선 작업의 진입점으로 활용할 수 있습니다.
