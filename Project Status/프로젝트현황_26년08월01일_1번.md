## 1. 종합 요약

AoID는 독립 개발자 협회를 위한 풀스택 플랫폼으로, 단순 회원·게시판 서비스 범위를 넘어 다음 기능을 하나의 운영 시스템으로 통합하고 있다.

- 이메일/JWT/Google·GitHub OAuth 기반 회원 인증과 등급·소속·관리자 권한
- 동적 게시판, 댓글, 좋아요, 임시저장, 대표 이미지, 리치 텍스트·미디어 편집기
- 협회 소개, 주요 사업, 홈 위젯, 헤더·푸터·테마·컨테이너 폭 관리자 설정
- 회원 앱 등록과 앱 비전, 통계, 피드백, 좋아요
- 상품, 장바구니, 주문, TossPayments 결제·환불·빌링·구독
- DevCoins 잔액·원장·충전·상품 구매
- 삼각형·선다형·막대척도형 DevSpectrum 검사, 진행 저장, 제출 이력, 전체 분석과 결과 리포트
- Gemini 기반 AI 게시글·댓글 활동 스케줄러와 관리자 모니터링
- 이미지·동영상 라이브러리, 휴지통, 중복 탐지, 사용처 탐색
- 동적 sitemap과 게시글·DevSpectrum 결과 SEO 렌더링
- 별도 Markdown 뉴스 제작 서브모듈인 NewsMaker

2026-08-01 현재 핵심 애플리케이션 소스는 Frontend 419개 TypeScript 파일 133,791줄, Backend 156개 TypeScript 파일 36,369줄로 합계 575개 파일 170,160줄이다. DB 마이그레이션은 92개다.

최근 개발은 DevSpectrum 3종 검사의 관리자 공통 체계, 막대척도 검사 진행 자동저장·재개, 결과 분석, 조합형 결과, 공통 3페이지 리포트, `result_style_type`, 관리자 리포트 설정에 집중되어 있다. 기능 폭은 넓고 최근 변화량도 크지만, 자동 테스트가 RichTextEditor와 단일 백엔드 미들웨어에 편중되어 있어 인증·결제·DevSpectrum·배포 회귀를 충분히 방어하지 못한다.

현재 최우선 정비 대상은 다음과 같다.

1. Toss webhook 요청 진위·재전송 멱등성 검증
2. 막대척도 비공개 결과 접근 제어와 사용자/관리자 API 계약 불일치
3. 신규 빈 DB에서 92개 JS 마이그레이션만으로 전체 스키마를 재현할 수 있는지 검증 및 누락 체인 정비
4. 원격 URL을 서버에서 가져오는 OG 이미지 프록시의 SSRF 방어
5. `optionalAuthenticate`의 계정 활성·현재 role 재검증
6. DevSpectrum 동적 리다이렉트, 6구간 반응형 적용, 결과 판형 overflow, 선택 성향·동점 결정 규칙 정합성
7. Backend 배포 락의 실패 시 해제, 동시 배포 차단, 테스트 게이트

- `npm start` — CRA 개발 서버

주의점:

- 실제 TypeScript는 `^4.9.5`다. 이전 문서의 `5.9.3` 표기는 Backend 버전과 혼동된 것이다.
- Router v7과 불필요한 `@types/react-router-dom ^5.3.3`이 함께 존재한다.
- React 19 + CRA 5 + TypeScript 4.9 조합은 현재 빌드 실행으로 호환성을 재검증할 필요가 있다.

### 6.5 6개 viewport 기준

단일 경계 정의는 `frontend/src/utils/viewport.ts`다.

| 구간 | 범위 |
| :--- | :--- |
| mobile | `< 768px` |
| HD | `768px <= width < 1280px` |
| FHD | `1280px <= width < 1920px` |
| QHD | `1920px <= width < 2560px` |
| UHD | `2560px <= width < 3840px` |

`devSpectrumViewport.ts`가 이 기준을 파생해 리포트 scale과 layout token을 제공한다. 그러나 전역 MUI theme에는 custom breakpoint가 등록되어 있지 않아 기본 `xs=0, sm=600, md=900, lg=1200, xl=1536`가 유지된다.

따라서 “경계 단일 소스 파일은 존재한다”는 사실과 “모든 화면이 6개 구간을 일관되게 적용한다”는 상태를 구분해야 한다. 후자는 아직 완성되지 않았다.

정확히 검증해야 할 경계:

`767, 768, 1279, 1280, 1919, 1920, 2559, 2560, 3839, 3840px`와 최소 모바일 320px. 자동 경계 테스트는 현재 없다.

## 8. 인증·권한 구조

### 8.1 필수 인증

`src/middleware/auth.ts`의 `authenticate`:

1. `auth_token` HTTP-only cookie 우선
2. 없으면 Bearer token 사용
3. JWT verify
4. `users`에서 `id, role, is_active` 재조회
5. 존재하지 않거나 비활성 계정은 401
6. JWT의 stale role 대신 DB 현재 role을 `req.user`에 반영

`isAdmin`은 현재 `req.user.role === 'admin'`을 요구한다. `adminRoutes.ts`는 최상단 `router.use(authenticate, isAdmin)`으로 관리자 전체를 보호한다.

### 8.2 선택 인증의 신뢰 차이

`optionalAuthenticate`는 토큰이 있으면 JWT만 검증하고 DB에서 사용자 존재·활성·현재 role을 재조회하지 않는다. 토큰 오류도 익명으로 통과시킨다.

영향 가능 영역:

- 비공개·임시 게시글 조회의 관리자 판정
- Triangle/MultipleChoice 결과 소유권·관리자 판정
- 탈퇴·비활성화 후 아직 만료되지 않은 JWT
- role 회수 후 stale admin payload

선택 인증도 token이 존재하는 경우 최소한 사용자 활성·현재 role을 DB에서 재확인하는 정책으로 통일하는 것이 안전하다.

### 8.3 회원·OAuth

- 이메일 가입과 bcrypt cost 10
- JWT cookie + response body token 하위 호환
- Google/GitHub Passport OAuth
- 이메일 인증·재발송·상태 확인
- 탈퇴·재활성화
- 등급·카테고리·소속 권한

CORS는 `FRONTEND_URL`을 쉼표로 분리해 다중 origin을 허용하지만 OAuth 성공·실패·탈퇴 redirect는 원문 환경변수를 단일 URL처럼 문자열 결합하는 경로가 남아 있다. 여러 origin을 넣으면 malformed redirect가 될 수 있으므로 `ALLOWED_ORIGINS`와 `CANONICAL_FRONTEND_URL`을 분리하는 것이 적절하다.

재활성화 endpoint는 OAuth 비활성 계정에서 password 없이 email 중심으로 동작하는 경로가 있어 계정 소유 증명 정책 재검토가 필요하다.

## 10. 결제·구독·DevCoins·상점

### 10.1 결제 흐름

`paymentController.confirmPayment`의 주요 경계:

1. 주문 소유권·금액·상태 확인
2. Toss confirm 외부 호출
3. payment/order/history DB transaction
4. commit 후 DevCoins 지급을 별도 transaction으로 수행

결제 DB commit 후 DevCoins 지급이 실패하면 결제 성공과 코인 잔액이 일시적으로 불일치할 수 있다. 재조정 job 또는 outbox/idempotent fulfillment 구조가 필요하다.

환불은 열린 DB transaction 안에서 Toss cancel 외부 호출을 수행한다. 외부 네트워크 지연 동안 DB lock을 오래 유지할 수 있으므로 상태 머신·보상 transaction 구조를 검토해야 한다.

### 10.2 Webhook

`POST /api/payments/webhook`은 공개 수신 경로인 것 자체는 일반적인 webhook 구조다. 그러나 현재 `controllers/payment/webhookController.ts`는 다음을 확인하지 않는다.

- Toss 서명 또는 shared secret
- raw body 기반 HMAC
- source 검증
- event ID 저장
- replay 방지
- 처리 멱등성

전역 `express.json()` 이후 처리하므로 raw body 검증 구조도 없다. 전체 payload 로그는 결제 데이터 노출 범위를 검토해야 한다. 처리 오류에도 HTTP 200을 반환하며, 가상계좌 완료 이력 insert가 재전송에 중복될 가능성이 있다.

### 10.3 구독

- billing key 발급·저장
- 첫 결제
- 정기 결제 scheduler
- 취소·상태 관리

scheduler는 매일 00:00 KST에 due subscription을 순차 처리한다. claim row, `FOR UPDATE SKIP LOCKED`, distributed lock, idempotency key가 없어 다중 인스턴스에서 중복 청구 위험 후보가 있다.

Toss 일반 결제는 mode별 `TOSS_LIVE_*`·`TOSS_TEST_*`, 일부 billing auth는 generic key를 사용한다. `.env.example`과 deploy workflow의 키 계약을 통일해야 한다.

### 10.4 DevCoins

`devcoinsService.spendDevCoins`는 `FOR UPDATE`로 잔액과 원장을 원자 처리한다. 이는 강점이다.

남은 점검:

- 자유 충전 order id unique/idempotency
- 결제 성공 후 코인 지급 재시도
- 환불 시 코인 회수와 사용 완료 상태
- 관리자 수동 지급 audit

### 10.5 상품·장바구니

- 공개 상품 조회
- 내 아이템·소유권
- DevCoins 단건·장바구니 구매
- 주문·장바구니
- 관리자 상품·구매 관리

재고 row lock 또는 조건부 stock update가 보이지 않는 경로가 있어 동시 구매 oversell 가능성을 통합 테스트해야 한다. 장바구니 구매는 transaction client 경계를 다시 정리할 필요가 있다.

- 제출 직전 eligibility 재검증
- 결과 범위와 조합 결과

대표 성향 선택 일부가 명시적 secondary ORDER BY 없이 조회 순서와 strict `>` first-win에 의존한다. 동점 결정 규칙을 DB와 UI 모두 명시해야 한다.

### 11.4 막대척도 검사

- signed slider 값을 좌·우 성향에 합산
- 진행 임시저장·재개
- 제출 이력
- overall/best-worst/pair
- 결과 style과 trait detail 표시 방식

정적 분석에서 확인된 차이:

- 검사 상세 조회에 active·grade 제한이 Triangle/MultipleChoice와 동일하지 않다.
- 제출 시 eligibility 재검증이 동일 수준으로 보이지 않는다.
- 결과 조회 route는 `optionalAuthenticate`지만 controller에서 `is_public` 또는 owner/admin을 일관되게 검사하지 않아 비공개 결과 노출 위험이 있다.
- Frontend의 공개 토글은 관리자 endpoint를 사용한다.

### 11.5 DevSpectrum 데이터 정합성 이슈

- `introController.ts`에서 JSONB `trait_ids`에 PostgreSQL array `ANY()` 형태를 적용하는 fallback이 남아 있다.
- selected trait ID 필터가 intro sequence/best-worst 계산에 일관되게 적용되지 않는다.
- Bar 선택 성향 update는 Triangle/MultipleChoice보다 검증·transaction·stale cleanup이 약하다.
- Intro의 bar-scale 분기가 삼각형 answer 흐름을 재사용하는 경로를 재검증해야 한다.
- keep-list delete SQL에서 숫자 ID를 `join(',')`하는 세 경로가 남아 있다. 현재 값 출처상 즉각적인 고신뢰 SQL injection으로 단정할 수는 없지만 프로젝트의 전면 파라미터화 원칙에는 맞지 않는다.
- 일부 controller가 요청 중 `ALTER TABLE ... IF NOT EXISTS` runtime DDL을 수행해 migration 책임과 실행 책임이 섞여 있다.

## 13. CI/CD와 배포

### 13.1 Frontend workflow

`frontend/.github/workflows/deploy.yml`:

1. main/master push
2. checkout
3. Node 18
4. `npm install`
5. `npm run build`, `CI: false`
6. EC2 frontend lock 생성
7. SCP로 build 전송
8. `/var/www/html` 복사·owner 변경
9. `nginx -t`
10. reload 후 lock 제거
11. `if: always()` 별도 lock cleanup

강점:

- Frontend lock은 항상 cleanup step이 있다.
- Nginx 설정 검증 후 reload한다.

개선점:

- `npm ci`가 아닌 `npm install`
- 테스트 단계 없음
- `CI: false`로 warning을 CI 실패로 처리하지 않음
- GitHub Actions `concurrency` 없음
- rollback artifact 없음
- 기존 `/var/www/html`을 원자적 release directory/symlink로 교체하지 않음

### 13.2 Backend workflow

`backend/.github/workflows/deploy.yml`:

1. main/master push
2. SSH 접속
3. backend lock 생성
4. 서버 repo fetch + hard reset 또는 clone
5. GitHub Secrets로 `.env` 재생성
6. `npm install`
7. `npm run build`
8. `npm run db:migrate`
9. PM2 restart/start/save
10. lock 제거
11. Nginx reload

강점:

- DB migration 자동 반영 규칙과 일치
- PM2 상태에 따라 restart/start 분기
- 배포 환경변수를 Secrets에서 공급

고위험 개선점:

- 중간 실패 시 lock을 제거하는 `if: always()` 또는 shell trap이 없음
- 실패 후 전체 사이트가 503에 남을 수 있음
- 동시 workflow를 막는 `concurrency` 없음
- lock 획득이 atomic하지 않음
- test/lint/typecheck gate 없음
- `npm ci` 미사용
- migration 이후 app restart 실패 시 rollback이 없음
- 배포 중 migration의 backward compatibility를 보장하는 단계가 없음

### 13.3 배포 원칙

- 수동 SSH 배포가 기본이 아님
- Push 후 GitHub Actions가 자동 배포
- Push 전 사용자 승인 필수
- DB migration은 Backend workflow에서 자동 실행
- Push 후 별도로 “배포할지” 묻지 않음

## 14. Nginx와 운영 인프라

운영 기준 실제 파일 경로는 `/etc/nginx/sites-available/aoid`다. 저장소의 `nginx/aoid_v1_260725.conf`, `nginx/aoid_v2_260726.conf`는 스냅샷이며 라이브 서버와 동일하다고 단정할 수 없다.

v2 주요 내용:

- `aoid.kr`, `www.aoid.kr`
- SSL/Certbot
- 50MB body
- frontend/backend lock 중 하나가 있으면 503
- `/maintenance.html`
- `/api` → localhost:5000
- `/uploads` → Backend, wildcard CORS와 1일 public cache
- `/sitemap.xml` → Backend
- 게시글·일부 DevSpectrum 결과 URL에서 bot만 SEO endpoint로 rewrite
- 일반 사용자는 React SPA

정비 필요:

- 일반 SPA root `/var/www/html`과 특수 SEO 경로 fallback root `/var/www/aoid/frontend/build`가 달라 버전 드리프트 가능
- DevSpectrum SEO route에 bar-scale이 없음
- `/uploads` 전체 공개·wildcard CORS·public cache 정책 재검토
- HTTP 80 server의 `return 404` 뒤 maintenance block은 사실상 도달 불가
- 저장소 스냅샷과 라이브 설정 동기화 자동화 없음
- CSP, HSTS, rate limit은 전역 include 여부를 운영 서버에서 확인해야 함
- `Docs/Nginx_SEO_Config.md`와 루트 README의 5MB 예시는 현재 50MB snapshot과 불일치

1. 승인된 계획은 구현과 검증을 모두 끝낸 후 결과를 보고한다.
2. 프로젝트 현황 문서는 `Project Status/프로젝트현황_YY년MM월DD일_N번.md` 새 파일로 작성한다.
3. Frontend/Backend 커밋 직후 루트 서브모듈 포인터 커밋을 함께 만든다.
4. Push 전 사용자에게 반드시 허락을 구한다.
5. 배포는 GitHub Actions가 자동 수행한다.
6. DB 변경은 로컬 `npm run db:migrate` 검증 후 push하며 운영 DB는 workflow가 자동 반영한다.
7. migration 파일은 CommonJS를 사용한다.
8. migration runner는 `npx node-pg-migrate`를 사용한다.
9. 서버와 DB session은 KST `Asia/Seoul`을 유지한다.
10. DevSpectrum 사용자 화면은 6개 viewport 경계를 단일 기준으로 적용한다.
11. 결과 PDF·이미지 대상은 `PrintPage`, zoom-to-fit, 수평 고정, SVG viewBox 원칙을 유지한다.
12. 사용자 첨부 이미지는 수정 완료 후 계속 기준 자료로 재사용하지 않는다.

## 22. 분석 근거와 한계

### 직접 확인한 자료

- 루트·세 서브모듈 Git 상태와 최근 커밋
- Frontend/Backend 파일 수·라인 수·대형 파일
- `App.tsx`, `index.tsx`, API client, viewport, report/capture 공통 코드
- Backend index, auth, database, route·controller·service 구조
- payment webhook
- migration runner와 최신 migrations
- 양쪽 deploy workflow
- Nginx v2 snapshot
- Frontend/Backend 테스트 구조
- NewsMaker 지침·목록·완료 색인
- 루트 README, Docs, scripts, semantic review, 기존 현황 문서

### 의도적으로 확인하지 않은 자료

- `.env`와 실제 secret 값
- 운영 서버 `/etc/nginx/sites-available/aoid`
- 운영 PM2·로그·DB 데이터
- GitHub Actions 실제 최근 run 결과
- Toss·OAuth 외부 콘솔
- PPTX·AI 바이너리 내부 메타데이터
- NewsMaker 기사 내용의 웹 사실 검증

### 실행하지 않은 검증

- build/test/typecheck
- migration up/down
- 브라우저·Playwright
- API·DB·결제 sandbox

따라서 코드상 직접 확인한 보안 결함은 우선 조치 대상으로 볼 수 있지만, 성능·동시성·브라우저 시각 문제는 재현 테스트로 영향도를 확정해야 한다.

## 23. 지원 준비 상태

현재 다음 작업에 즉시 착수할 수 있는 수준으로 구조와 위험 지도를 확보했다.

- Frontend 페이지·컴포넌트·라우트·API 계약 수정
- Backend route/controller/service와 권한 로직 수정
- PostgreSQL migration 작성·재현성 정비
- DevSpectrum 3종 scoring·관리·리포트·6구간 반응형 보완
- RichTextEditor·게시판·미디어 기능 개선
- TossPayments·DevCoins·구독 보안 및 멱등성 강화
- AI scheduler·Gemini 활동 안정화
- Nginx·GitHub Actions 배포 신뢰성 개선
- 테스트 체계 확장
- NewsMaker·루트 문서·자산 운영 정리

프로젝트는 기능적으로 매우 넓은 통합 플랫폼 단계에 도달했지만, 현재 품질 수준을 “모든 기능 완료·검증 완료”로 표현하기는 어렵다. 가장 정확한 상태는 **핵심 기능이 폭넓게 구현되어 있고 DevSpectrum 보고서 체계가 빠르게 확장되는 중이며, 보안·DB 재현성·권한/API 정합성·자동 테스트·배포 실패 복구를 다음 안정화 축으로 삼아야 하는 상태**다.
